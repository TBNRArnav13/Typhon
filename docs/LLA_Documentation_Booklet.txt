CHAPTER 4 :  Product Requirements Document (PRD)
────────────────────────────────────────────────────────────────────────────────

4.1  Product Overview & Purpose

The Unified DoS/DDoS Detection System is designed to provide a comprehensive,
hybrid approach to network threat detection. The system combines behavior-based
anomaly detection (Kitsune) with supervised classification (XGBoost) to analyze
network traffic files and produce actionable security intelligence.

Purpose:
  - Detect both known and unknown (zero-day) DoS/DDoS attacks in network
    traffic data
  - Classify detected threats into specific attack categories with confidence
    scores
  - Generate structured output reports suitable for security operations and
    incident response workflows
  - Provide a configurable, extensible platform that can be adapted to
    different network environments and detection requirements

The hybrid approach maximizes detection accuracy by leveraging XGBoost's
high-precision classification for known attack patterns, while Kitsune's
anomaly detection provides coverage for novel, previously unseen threats.


4.2  Supported Input Formats

The system supports three primary input formats:

  1. CSV (Comma-Separated Values):
     - Flow-based network datasets with pre-extracted features
     - Expected to contain the 33 selected features defined in config.yaml
     - Label column (optional) — used for evaluation when available
     - Maximum file size: 4096 MB (configurable via data_loading.max_file_size_mb)
     - Row limit per file: 100,000 rows (configurable via data_loading.max_rows_per_file)

  2. PCAP (Packet Capture):
     - Raw packet capture files from network interfaces or monitoring tools
     - Processed through the integrated Scapy-based feature extraction pipeline
     - Supports bidirectional flow aggregation via 5-tuple identification
       (Source IP, Destination IP, Source Port, Destination Port, Protocol)
     - Extracted features are saved as CSV in the output directory for
       reproducibility

  3. PCAPNG (Next Generation Packet Capture):
     - Extended packet capture format with enhanced metadata support
     - Processed using the same pipeline as standard PCAP files
     - Supports all features available in PCAP processing

Dataset Size Considerations:
  - Small datasets: ~100 MB — processed entirely in memory
  - Medium datasets: 100 MB – 1 GB — processed with row-limiting
  - Large datasets: 1 GB – 4 GB — processed with chunk-based loading
  - Maximum supported: 4 GB (configurable upper limit)


4.3  Acceptance Criteria

The system must satisfy the following acceptance criteria to be considered
production-ready:

  1. Successfully processes multi-gigabyte CSV datasets on local hardware
     without memory overflow errors

  2. Detects both known DoS/DDoS attack types (10 categories) and unknown
     anomalous traffic patterns

  3. Produces correct file-level classification verdicts (SAFE, SUSPICIOUS,
     or MALICIOUS) based on flow analysis

  4. Generates a structured Markdown summary report (Report.md) containing
     detection statistics, model information, flow breakdowns, and
     timestamped metadata

  5. Outputs JSON prediction files categorized into benign, DoS/DDoS, and
     anomaly classifications

  6. Provides confidence scores for all detection results, combining
     XGBoost class probability with Kitsune anomaly severity

  7. Executes via a single command interface — either through run.bat
     (Windows launcher) or direct Python invocation (python run.py)


4.4  Success Metrics

The following quantitative and qualitative metrics define the system's success:

  Quantitative Metrics:
  - Detection Accuracy:  ≥ 95% on known DoS/DDoS attack types
  - False Positive Rate: ≤ 5% on clean benign traffic
  - Zero-Day Detection:  Kitsune anomaly scores reliably exceed threshold
                         for novel attack traffic
  - Processing Speed:    Complete analysis of a 100 MB CSV in under
                         60 seconds on standard hardware

  Qualitative Metrics:
  - Reproducibility:     Identical inputs produce consistent detection
                         results across runs
  - Interpretability:    Each flow prediction includes a human-readable
                         reason field explaining the detection logic
  - Extensibility:       New attack types or features can be added through
                         configuration changes and model retraining without
                         modifying core source code
  - Scalability:         System architecture supports future migration to
                         real-time detection and REST API deployment

5.2  Modular Design Philosophy

The system is built on a modular architecture with the following design
principles:

  1. Single Responsibility: Each module handles one specific concern:
     - input_handler.py → File validation and format routing
     - data_loader.py → CSV loading and feature standardization
     - feature_extractor.py → PCAP-to-feature conversion
     - xgboost_model.py → Supervised classification
     - kitsune.py → Unsupervised anomaly detection
     - hybrid.py → Decision fusion and verdict generation
     - reporting.py → Output formatting and file generation
     - utils.py → Logging and hardware detection utilities

  2. Loose Coupling: Modules communicate through well-defined interfaces
     (DataFrames and dictionaries). No module directly imports another
     module's internal state.

  3. Configuration-Driven: All tunable parameters (paths, hyperparameters,
     features, thresholds) are externalized to config.yaml. No hardcoded
     values exist in source code for configurable parameters.

  4. Centralized Orchestration: run.py serves as the sole entry point and
     orchestrator. It manages the execution flow, model loading, and
     coordination between components.

5.4  Component Interaction Flow

The components interact in the following sequence during a detection run:

  1. Entry Point (run.py):
     - Parses command-line arguments or presents interactive menu
     - Loads config.yaml into a global CONFIG dictionary
     - Creates a timestamped output directory structure

  2. Input Handling (src/input_handler.py):
     - Validates the input file exists and is a supported format
     - Routes CSV files to data_loader.py
     - Routes PCAP/PCAPNG files to feature_extractor.py

  3. Data Processing:
     a) CSV Path (src/data_loader.py):
        - Reads CSV with pandas
        - Normalizes column names to lowercase
        - Selects the 33 configured features
        - Fills missing values with 0.0
     b) PCAP Path (src/feature_extractor.py):
        - Reads packets using Scapy's rdpcap()
        - Groups packets into bidirectional flows using 5-tuples
        - Computes 33 statistical features per flow
        - Returns a DataFrame with the same schema as CSV processing

  4. Model Inference:
     - XGBoost: Produces class label (0=Benign, 1=DoS) and probability
       per flow
     - Kitsune: Computes RMSE reconstruction error per flow, compares
       against dynamic threshold (mean + k × std)

  5. Decision Fusion (models/hybrid.py):
     - Receives both model outputs
     - Applies hierarchical decision logic
     - Applies heuristic safety overrides (broadcast, multicast detection)
     - Computes combined confidence score
     - Assigns final verdict and human-readable reason

  6. Output Generation (src/reporting.py):
     - Saves categorized JSON prediction files
     - Generates Markdown summary report (Report.md)
     - Writes technical debug log

6.4  Model Hyperparameters

  XGBoost Configuration:
  ─────────────────────
    xgboost:
      max_depth: 6                   # Maximum tree depth
      learning_rate: 0.1             # Step size shrinkage (eta)
      n_estimators: 100              # Number of boosting rounds
      objective: "binary:logistic"   # Binary classification objective
      tree_method: "auto"            # Auto-selects gpu_hist if GPU available

  - max_depth (6): Controls model complexity. Higher values increase
    accuracy but risk overfitting. Value of 6 balances performance and
    generalization for network flow classification.

  - learning_rate (0.1): Controls the contribution of each tree. Lower
    values require more estimators but typically produce better
    generalization.

  - n_estimators (100): Number of gradient-boosted trees. Combined with
    learning_rate=0.1, this provides a good balance of accuracy and
    training speed.

  - objective ("binary:logistic"): Binary classification with logistic
    regression output. Produces probability scores between 0 and 1.

  - tree_method ("auto"): Automatically selects the best tree construction
    algorithm. Switches to "gpu_hist" when a CUDA-enabled GPU is detected
    by the system's hardware detection utility.

  Kitsune Configuration:
  ──────────────────────
    kitsune:
      max_autoencoder_size: 10       # Maximum neurons per autoencoder
      learning_rate: 0.001           # Autoencoder learning rate
      hidden_ratio: 0.75            # Hidden layer size ratio
      feature_map_min: 1             # Minimum features per sub-autoencoder
      feature_map_max: 10            # Maximum features per sub-autoencoder
      threshold_std_factor: 3.0      # Anomaly threshold sensitivity

  - max_autoencoder_size (10): Maximum number of input neurons per
    individual autoencoder in the ensemble.

  - learning_rate (0.001): Learning rate for autoencoder weight updates
    during training.

  - hidden_ratio (0.75): Ratio of hidden layer size to input size.
    A value of 0.75 means the hidden layer has 75% of the input dimensions,
    creating a compression bottleneck for reconstruction learning.

  - feature_map_min/max (1/10): Range controlling how many features are
    assigned to each sub-autoencoder in the ensemble. The feature mapping
    algorithm distributes the 33 input features across multiple small
    autoencoders.

  - threshold_std_factor (3.0): Number of standard deviations above the
    mean RMSE to set the anomaly detection threshold. Higher values make
    detection less sensitive (fewer false positives but may miss subtle
    attacks). Formula: threshold = mean_rmse + 3.0 × std_rmse

    b) Can be extracted from raw PCAP files via the FeatureExtractor —

    c) Capture the key behavioral characteristics that distinguish

6.6  Detection Thresholds

  thresholds:
    malicious_file_ratio: 0.30

  - malicious_file_ratio (0.30): The proportion of flows that must be
    classified as malicious or anomalous for a file to receive a
    MALICIOUS or SUSPICIOUS verdict.

    Interpretation:
    - If ≥ 30% of flows in a file are flagged as DoS/DDoS or anomalous,
      the file is classified as MALICIOUS.
    - If the ratio is below 30% but anomalies are present, the file may
      be classified as SUSPICIOUS.
    - If no significant anomalies or malicious flows are detected, the
      file is classified as SAFE.

  Additionally, the Kitsune anomaly threshold is derived dynamically:
    - threshold = mean_rmse + threshold_std_factor × std_rmse
    - With threshold_std_factor = 3.0, this corresponds to approximately
      99.7% of the normal distribution for benign traffic
    - Flows with RMSE above this threshold are flagged as anomalous

7.1  Supported File Formats (CSV, PCAP, PCAPNG)

The system accepts three network traffic file formats:

  1. CSV (Comma-Separated Values):
     - Flow-based datasets exported from network analysis tools (CICFlowMeter,
       Wireshark statistics, custom exporters).
     - Expected to contain pre-computed flow-level features.
     - The most efficient format — no packet-level processing required.
     - Recognized by extension: .csv

  2. PCAP (Packet Capture):
     - Raw packet-level captures from network interfaces, tcpdump, or
       Wireshark.
     - Requires full feature extraction pipeline (Scapy-based processing).
     - Recognized by extension: .pcap

  3. PCAPNG (Next Generation Packet Capture):
     - Modern packet capture format with additional metadata (interface
       information, comments, name resolution).
     - Processed identically to standard PCAP files.
     - Recognized by extension: .pcapng

Both PCAP and PCAPNG files are processed through the same feature extraction
pipeline (FeatureExtractor), which converts raw packets into flow-level
statistical features matching the CSV schema.


7.2  File Validation & Routing Logic

Input handling is managed by the InputHandler class (src/input_handler.py),
which performs two primary functions: validation and routing.

Validation (validate_file method):
  Step 1:  Verify the file exists on disk using os.path.exists().
           If the file is not found, log an error and return False.

  Step 2:  Extract the file extension using os.path.splitext().
           Convert the extension to lowercase for case-insensitive comparison.

  Step 3:  Check the extension against the supported list:
             ['.csv', '.pcap', '.pcapng']
           If the extension is not supported, log an error and return False.

  Step 4:  Return True if both checks pass.

Routing (process_file method):
  After validation, the file is routed to the appropriate processor:

    +---------------------+---------------------------+
    | Extension           | Processor                 |
    +---------------------+---------------------------+
    | .csv                | load_csv() from           |
    |                     | data_loader.py            |
    +---------------------+---------------------------+
    | .pcap, .pcapng      | FeatureExtractor.         |
    |                     | extract_features() from   |
    |                     | feature_extractor.py      |
    +---------------------+---------------------------+

  For PCAP/PCAPNG files:
    - The FeatureExtractor is instantiated with the system configuration.
    - Features are extracted and returned as a pandas DataFrame.
    - If extraction produces an empty DataFrame or None, an error is logged
      and None is returned.

  For CSV files:
    - The file is loaded directly via load_csv() with the configured features.
    - The DataFrame is returned for downstream processing.

  Both paths produce a pandas DataFrame with the same 33-feature schema,
  ensuring uniform input to the detection layer.


7.3  Error Handling Strategy

The input handling module employs a fail-fast strategy with detailed logging:

  1. File Not Found:
     - Error level: ERROR
     - Message: "File not found: {filepath}"
     - Result: Returns None — the pipeline halts gracefully.

  2. Unsupported Format:
     - Error level: ERROR
     - Message: "Unsupported file format: {ext}"
     - Result: Returns None — prevents processing of incompatible files.

  3. PCAP Extraction Failure:
     - Error level: ERROR
     - Message: "Failed to extract features from PCAP."
     - Result: Returns None — typically caused by corrupted captures or
       files with no IP packets.

  4. CSV Loading Failure:
     - Error level: ERROR
     - Message: Propagated from data_loader.py with specific exception details.
     - Result: Returns None.

All errors are logged through the centralized logger (src/utils.py), which
writes to both the console and the technical debug log file. The pipeline
is designed to never throw unhandled exceptions — all errors are caught,
logged, and result in a None return that the orchestrator (run.py) handles.

CHAPTER 8 :  Feature Extraction

8.1  PCAP Processing Pipeline (Scapy)

When a PCAP or PCAPNG file is provided, the system invokes the
FeatureExtractor class (src/feature_extractor.py) to convert raw packets
into flow-level statistical features. The pipeline operates in three phases:

  Phase 1 — Packet Reading:
    - Uses Scapy's PcapReader for memory-efficient streaming (reads packets
      one at a time instead of loading the entire file).
    - Filters for IP-layer packets only (packets without an IP layer are
      silently skipped).
    - Extracts per-packet metadata: source/destination IP, source/destination
      port, protocol number, and timestamp.
    - Progress is logged every 10,000 packets.

  Phase 2 — Flow Aggregation:
    - Packets are grouped into bidirectional flows using canonical 5-tuple
      keys (see Section 8.3).
    - A defaultdict stores each flow's packets and direction labels.
    - The first packet of each flow determines the "forward" direction.
    - Subsequent packets are classified as forward (direction=1) or
      backward (direction=-1) based on the initiator identity.

  Phase 3 — Feature Computation:
    - For each aggregated flow, the _calculate_flow_stats() method computes
      33 statistical features across 5 categories (see Section 8.4).
    - Results are compiled into a pandas DataFrame.
    - Missing features are filled with 0.0.
    - The final DataFrame includes both flow identifiers (src_ip, dst_ip,
      src_port, dst_port, protocol) and the 33 selected features.


8.2  Bidirectional Flow Analysis

The system treats network conversations as bidirectional flows. This means
that packets from Host A to Host B and packets from Host B back to Host A
are aggregated into a single flow record.

Why Bidirectional?
  - DDoS attacks exhibit asymmetric traffic patterns (many requests, few
    responses). Bidirectional analysis captures this asymmetry through
    separate forward and backward statistics.
  - Reduces the number of flows by approximately 50%, improving efficiency.
  - Produces richer features — the ratio between forward and backward
    metrics is a powerful indicator of attack behavior.

Direction Determination:
  The first packet observed for a given 5-tuple sets the forward direction.
  All subsequent packets are classified by comparing their source IP and
  source port against the initiator:

    - Match initiator   →  Forward (direction = 1)
    - No match          →  Backward (direction = -1)

  This approach correctly handles:
    - Standard TCP request/response conversations.
    - UDP-based floods (predominantly one-directional).
    - Mixed protocols sharing the same endpoint pairs.

  Packets in each direction are separated into fwd_pkts and bwd_pkts lists,
  which are used independently for computing directional statistics.


8.3  5-Tuple Flow Identification

Each network flow is uniquely identified by a 5-tuple:

    (Source IP, Destination IP, Source Port, Destination Port, Protocol)

To ensure bidirectional aggregation, the system creates canonical keys by
sorting the IP addresses:

    if src_ip < dst_ip:
        key = (src_ip, dst_ip, src_port, dst_port, protocol)
    else:
        key = (dst_ip, src_ip, dst_port, src_port, protocol)

This guarantees that packets flowing A→B and B→A produce the same key,
enabling them to be aggregated into a single bidirectional flow.

Port Extraction:
  - TCP packets: sport and dport extracted from the TCP header.
  - UDP packets: sport and dport extracted from the UDP header.
  - Other protocols (ICMP, etc.): sport and dport default to 0.

Protocol Number:
  - Extracted from the IP header's proto field.
  - Common values: 6 (TCP), 17 (UDP), 1 (ICMP).


8.4  Feature Categories

The 33 features are organized into 5 categories, each capturing a different
behavioral aspect of network traffic:


  8.4.1  Packet Counts (Volume)

  These features measure the volume of traffic in each direction:

    - total fwd packets:       Count of packets in the forward direction.
    - total backward packets:  Count of packets in the backward direction.

  Computed by counting packets where direction == 1 (forward) or
  direction == -1 (backward).

  Attack Signature: DDoS attacks typically show massive forward packet
  counts with disproportionately few backward packets (reflection attacks)
  or extremely high counts in both directions (volumetric floods).


  8.4.2  Packet Lengths (Size Dynamics)

  Statistical measures of packet sizes in bytes, computed separately for
  forward and backward directions:

    Forward:
      - fwd packet length max, min, mean, std
      - total length of fwd packets

    Backward:
      - bwd packet length max, min, mean, std
      - total length of bwd packets

  Computed using the _set_stat_block() helper method, which calculates
  numpy max, min, mean, and std over the byte-length of each packet.
  For empty packet sets (e.g., no backward packets in a unidirectional
  flow), all values default to 0 via _set_zero_stat_block().

  Attack Signature: Attack traffic often has uniform packet sizes (same
  payload repeated), resulting in very low standard deviation. Legitimate
  traffic tends to have variable packet sizes.


  8.4.3  Inter-Arrival Times — IAT (Timing)

  Inter-arrival time is the time gap between consecutive packets, measured
  in microseconds. Computed at three levels:

    Flow-level (overall):
      - flow iat mean, std, max, min
      Calculated from sorted timestamps of all packets in both directions.

    Forward-only:
      - fwd iat total, mean, std, max, min
      Calculated from sorted timestamps of forward packets only.

    Backward-only:
      - bwd iat total, mean, std, max, min
      Calculated from sorted timestamps of backward packets only.

  IAT computation uses numpy's diff() function on sorted timestamp arrays,
  multiplied by 1e6 to convert from seconds to microseconds.

  For flows with 0 or 1 packet in a direction, all IAT values default to 0.

  Attack Signature: DDoS flooding attacks produce extremely small and
  consistent inter-arrival times (high packet rate). Normal traffic has
  variable and generally larger IATs.


  8.4.4  TCP Flags (Behavior)

  Flag counters track the presence of specific TCP control flags in each
  direction:

    - fwd psh flags:  Count of PSH (Push) flags in forward packets.
    - bwd psh flags:  Count of PSH flags in backward packets.
    - fwd urg flags:  Count of URG (Urgent) flags in forward packets.
    - bwd urg flags:  Count of URG flags in backward packets.

  Computed by iterating over all TCP packets and checking the flags field
  using Scapy's packet representation. Flags are converted to string form
  and checked for 'P' (PSH) and 'U' (URG) characters.

  Non-TCP packets (UDP, ICMP) do not contribute to flag counters.

  Attack Signature: SYN flood attacks show unusual flag patterns. DoS
  tools often set specific flag combinations. URG flags are rare in
  legitimate traffic and may indicate protocol abuse.


  8.4.5  Rate Calculations

  Rate features measure the throughput and packet rate of the flow:

    - flow bytes/s:    Total bytes (forward + backward) divided by flow
                        duration in seconds.
    - flow packets/s:  Total packets divided by flow duration in seconds.

  If the flow duration is 0 seconds (single-packet flow), both rates
  default to 0 to avoid division-by-zero errors.

  Attack Signature: DDoS attacks produce abnormally high byte and packet
  rates compared to normal traffic baselines.

After feature computation, the FeatureExtractor standardizes the output:

  1. Missing Feature Filling:
     Any feature from the selected_features list (config.yaml) that was not
     computed is added to the DataFrame with a default value of 0.0. This
     handles edge cases like PCAP files with only UDP traffic (no TCP
     flags).

  2. Column Selection:
     The returned DataFrame contains:
       - 5 identifier columns: src_ip, dst_ip, src_port, dst_port, protocol
       - 33 feature columns (matching config.yaml's selected_features)
     Only columns that exist in the DataFrame are returned (filtered via
     list intersection).

  3. Schema Consistency:
     The output DataFrame's feature columns are identical in name and order
     to those produced by the CSV loading path (data_loader.py), ensuring
     that the detection layer receives uniform input regardless of the
     original file format.

To improve the model's accuracy against State-Exhaustion and Slow-Rate
attacks, the following features have been identified as optional additions
for future fine-tuning. These features are not part of the current 33-feature
set but can be integrated after primary approvals and model revalidation.


  8.7.1  Critical TCP Flags (SYN, ACK, RST, FIN)

  Proposed Features:
    - SYN Flag Cnt
    - ACK Flag Cnt
    - RST Flag Cnt
    - FIN Flag Cnt

  Reason for Addition:
    - SYN Floods: Explicit SYN counting enables detection of SYN-heavy,
      ACK-light traffic patterns typical of half-open connection attacks.
    - ACK Floods: High ACK counts without corresponding data may indicate
      reflection or state-table exhaustion attacks.
    - Scanning Activity: Elevated RST or FIN counts strongly indicate port
      scanning or reconnaissance phases preceding DDoS attacks.

  The current system tracks only PSH and URG flags. Adding SYN, ACK, RST,
  and FIN counters would provide coverage for connection-state manipulation
  attacks that exploit the TCP three-way handshake.


  8.7.2  TCP Window Size

  Proposed Features:
    - Init Fwd Win Byts  (Initial forward window size in bytes)
    - Init Bwd Win Byts  (Initial backward window size in bytes)

  Reason for Addition:
    - Bot Fingerprinting: TCP window size is determined by the operating
      system's TCP stack. Legitimate systems exhibit standardized patterns
      based on their OS version and configuration.
    - Detection Logic: IoT botnets (e.g., Mirai) or scripted attack tools
      (e.g., hping3) often use hardcoded or non-standard window sizes,
      enabling differentiation between bots and legitimate clients.

  These features would enhance the system's ability to distinguish
  machine-generated attack traffic from legitimate user traffic based
  on TCP stack fingerprinting.


  8.7.3  Active / Idle Times

  Proposed Features:
    - Idle Mean  (Mean idle time between active periods)
    - Idle Std   (Standard deviation of idle times)

  Reason for Addition:
    - Slow-Rate Attacks (Slowloris): These attacks maintain open connections
      by periodically sending partial HTTP requests, keeping the connection
      alive while consuming server resources.
    - Detection Logic: While Flow Duration measures total session time,
      Idle Mean specifically exposes the intentional waiting behavior
      typical of slow-rate attacks. A high idle mean combined with a
      long flow duration is a strong indicator of Slowloris or similar
      slow-rate DoS strategies.

  These features would extend detection coverage to application-layer
  slow-rate attacks, which are currently harder to detect using only
  packet volume and timing features.

CHAPTER 9 :  Data Loading & Preprocessing

9.1  CSV Data Loading (data_loader.py)

The data_loader module provides two primary functions:

  1. load_csv():
     Loads a single CSV file and returns a cleaned DataFrame with selected
     features. This is the primary function called during detection mode.

     Function Signature:
       load_csv(filepath, selected_features=None, label_override=None)

     Parameters:
       - filepath: Absolute or relative path to the CSV file.
       - selected_features: Optional list of feature column names. If None,
         uses the selected_features from config.yaml.
       - label_override: Optional string to override all labels in the
         dataset (used during training to force benign/dos labels).

  2. combine_datasets():
     Loads and merges multiple datasets for training. Combines benign and
     DoS CSVs into a single training DataFrame.

     Function Signature:
       combine_datasets(benign_path, dos_dir)

     Parameters:
       - benign_path: Path to the benign traffic CSV.
       - dos_dir: Path to the directory containing DoS attack CSVs.

     Behavior:
       - Loads the benign CSV via load_csv().
       - Iterates over all .csv files in the DoS directory, loading each.
       - Concatenates all DataFrames using pd.concat(axis=0, ignore_index=True).
       - Logs the final combined shape.


9.2  Memory Management & Row Limits

The data loader implements two safety mechanisms to prevent memory
exhaustion:

  1. File Size Check:
     Before loading, the file size is checked against the configured limit:
       max_file_size_mb = CONFIG['data_loading']['max_file_size_mb']
                        = 4096 (default)

     If file_size > max_file_size_mb, loading is rejected with an error log.
     This prevents accidental processing of extremely large files.

  2. Row Limit:
     When loading with pandas, the nrows parameter limits the number of
     rows read:
       max_rows_per_file = CONFIG['data_loading']['max_rows_per_file']
                         = 100000 (default)

     pd.read_csv(filepath, nrows=max_rows) reads only the first 100,000
     rows. This is particularly important for multi-GB datasets where
     loading all rows would exceed available RAM.

     If max_rows is set to None in the config, all rows are loaded
     (no limit applied).


9.3  Column Standardization

After loading the CSV, column names are standardized to ensure consistent
matching with the configured feature list:

    df.columns = df.columns.str.strip().str.lower()

This two-step normalization:
  1. str.strip() — Removes leading and trailing whitespace from column names.
  2. str.lower() — Converts all column names to lowercase.

This handles common inconsistencies in CSV exports:
  - " Flow Duration " → "flow duration"
  - "Total Fwd Packets" → "total fwd packets"
  - "FWD_PACKET_LENGTH_MAX" → "fwd_packet_length_max"

The configured selected_features list is also normalized using the same
transformation:
    selected_features = [f.strip().lower() for f in selected_features]

This ensures that feature matching is case-insensitive and whitespace-
tolerant.


9.4  Feature Selection & Intersection

Not all CSV files contain exactly the same columns. The data loader handles
this through intersection-based feature selection:

  1. The desired features are taken from config.yaml's selected_features
     list (33 features).

  2. The label column is automatically appended to the selection list if
     it exists in the DataFrame:
       if 'label' in df.columns and 'label' not in selected_features:
           selected_features.append('label')

  3. The intersection of desired features and available columns is computed:
       existing_cols = [c for c in selected_features if c in df.columns]
       missing_cols = [c for c in selected_features if c not in df.columns]

  4. Missing columns are logged as warnings (WARNING level) but do not
     cause the loading to fail. The DataFrame is returned with only the
     existing columns.

  5. The DataFrame is then filtered to keep only the intersection columns:
       df = df[existing_cols]

This approach ensures that:
  - CSVs with extra columns (beyond the 33) are trimmed appropriately.
  - CSVs missing some columns still load successfully with partial features.
  - The label column is preserved when available for training and evaluation.


9.5  Data Cleaning (Infinite Values, NaN Handling)

After feature selection, the data loader performs two cleaning operations:

  1. Infinite Value Replacement:
       df.replace([float('inf'), float('-inf')], float('nan'), inplace=True)

     Both positive and negative infinity values are replaced with NaN. This
     handles edge cases in network flow calculations where division by zero
     produces infinity (e.g., flow bytes/s when duration is near zero).

  2. NaN Row Removal:
       df.dropna(inplace=True)

     All rows containing any NaN value (including those just converted from
     infinity) are removed from the DataFrame.

  This strategy ensures that no invalid numerical values reach the ML
  models, which could cause training instability or prediction errors.


9.6  Label Processing (Binary Encoding)

During training, the system uses binary labels:
  - 0 = Benign (normal traffic)
  - 1 = DoS/DDoS (attack traffic)

The label_override parameter in load_csv() allows explicit label assignment:
  - When loading benign data: label_override is not used; the label column
    from the CSV is preserved (already contains "BENIGN").
  - When loading DoS data: each file retains its original attack type label.

The binary encoding for XGBoost training is performed downstream in run.py:
  - The label column is checked for the string "BENIGN" (case-insensitive).
  - Benign flows are mapped to 0, all other labels are mapped to 1.
  - This creates a binary classification target for the XGBoost model.


9.7  Multi-File Dataset Aggregation

The combine_datasets() function handles the training data preparation
workflow:

  Step 1:  Load the benign dataset from the configured path:
             Dataset/PolishedBenign/Polished_benign.csv

  Step 2:  Iterate over all CSV files in the DoS directory:
             Dataset/PolishedDos/
           Each of the 10 DoS attack type CSVs is loaded individually.

  Step 3:  Each loaded DataFrame is appended to a list.

  Step 4:  All DataFrames are concatenated vertically:
             combined_df = pd.concat(dfs, axis=0, ignore_index=True)
           The ignore_index=True parameter resets the row indices to
           create a continuous sequence.

  Step 5:  The final combined shape is logged for verification.

  The result is a single DataFrame containing all benign and DoS flows
  with consistent features, ready for model training. If no DataFrames
  were successfully loaded (all files failed), None is returned.

CHAPTER 10 :  XGBoost Classifier Model
────────────────────────────────────────────────────────────────────────────────

10.1  Model Overview & Justification

XGBoost (eXtreme Gradient Boosting) is a supervised machine learning
algorithm used in this system for binary classification of network flows as
either Benign (0) or DoS/DDoS (1).

Why XGBoost was chosen:
  - High accuracy on tabular/structured data — consistently outperforms
    other algorithms (Random Forest, SVM, Logistic Regression) in
    network intrusion detection benchmarks.
  - Fast inference speed — critical for processing hundreds of thousands
    of flows per detection run.
  - Native GPU acceleration — via the hist tree method with CUDA support,
    enabling rapid training on large datasets.
  - Built-in regularization — prevents overfitting through L1/L2
    regularization and max_depth constraints.
  - Handles missing features gracefully — important for real-world network
    data where some features may be unavailable.

The XGBoost model is implemented in models/xgboost_model.py as the
XGBoostDetector class.


10.2  Algorithm: Gradient Boosted Decision Trees

XGBoost implements the Gradient Boosted Decision Trees (GBDT) algorithm:

  1. An initial prediction is made (base learner — typically the mean).
  2. The residuals (errors) between the prediction and actual labels are
     calculated.
  3. A new decision tree is trained to predict these residuals.
  4. The new tree's predictions are added to the ensemble, scaled by the
     learning rate (eta).
  5. Steps 2–4 repeat for n_estimators iterations (100 rounds).

Each successive tree corrects the errors of the previous ensemble, gradually
improving accuracy. The final prediction is the sum of all tree outputs,
passed through a logistic (sigmoid) function to produce a probability:

    P(DoS) = sigmoid(sum of all tree outputs)

If P(DoS) > 0.5, the flow is classified as DoS/DDoS (label = 1).
If P(DoS) <= 0.5, the flow is classified as Benign (label = 0).


10.3  Architecture & Hyperparameters

  10.3.1  max_depth, learning_rate, n_estimators

  +-------------------+--------+---------------------------------------------+
  | Parameter         | Value  | Purpose                                     |
  +-------------------+--------+---------------------------------------------+
  | max_depth         |   6    | Maximum depth of each decision tree.        |
  |                   |        | Controls model complexity. Deeper trees      |
  |                   |        | capture more patterns but risk overfitting.  |
  +-------------------+--------+---------------------------------------------+
  | learning_rate     |  0.1   | Step size shrinkage (eta). Each tree's       |
  |                   |        | contribution is multiplied by this factor.   |
  |                   |        | Lower = more trees needed, better            |
  |                   |        | generalization.                              |
  +-------------------+--------+---------------------------------------------+
  | n_estimators      |  100   | Total number of boosting rounds (trees).     |
  |                   |        | Combined with learning_rate=0.1, provides    |
  |                   |        | a good accuracy/speed balance.               |
  +-------------------+--------+---------------------------------------------+


  10.3.2  Objective Function (Binary Logistic)

  The objective function is set to "binary:logistic":
    - Optimizes log-loss (cross-entropy) between predicted probabilities
      and actual binary labels (0 or 1).
    - Outputs probability scores between 0.0 and 1.0 for each flow.
    - The 0.5 threshold separates Benign (< 0.5) from DoS/DDoS (>= 0.5).

  Evaluation metrics used during training:
    - logloss: Primary optimization metric.
    - error: Classification error rate for monitoring.


  10.3.3  Tree Method & GPU Acceleration

  The tree construction method is selected automatically based on hardware:

    - CPU mode: tree_method = "hist" with device = "cpu"
      Uses the histogram-based algorithm for efficient CPU training.

    - GPU mode: tree_method = "hist" with device = "cuda"
      Activated when nvidia-smi is detected (GPU drivers present).
      Provides 5-10x speedup for training on large datasets.

  Hardware detection is performed by the get_device() function
  (src/utils.py), which:
    1. Checks for CUDA availability via torch.cuda.is_available() (PyTorch).
    2. Runs nvidia-smi subprocess to confirm GPU driver presence (XGBoost).
    3. Returns a dictionary with device information for both frameworks.


10.4  Training Process — Step by Step

  10.4.1  Phase 1: Data Preparation

  Training begins in the train_xgboost() function (run.py):
    1. Load benign traffic: Dataset/PolishedBenign/Polished_benign.csv
    2. Load DoS traffic: All 10 CSVs from Dataset/PolishedDos/
    3. Combine using combine_datasets() into a single DataFrame.
    4. The combined dataset contains both benign and attack flows with
       the 33 selected features plus a label column.


  10.4.2  Phase 2: Feature Extraction & Label Encoding

    1. The label column is converted to binary:
         label_encoded = 0 if label.strip().upper() == "BENIGN" else 1
    2. Feature matrix X = all columns except label.
    3. Target vector y = the encoded label column.
    4. X and y are passed as numpy arrays to the training function.


  10.4.3  Phase 3: Hardware Detection (GPU/CPU)

  Hardware is detected during XGBoostDetector.__init__(), which calls
  get_device() once at instantiation time and stores the result in
  self.device_info.

  Inside XGBoostDetector.train():
    1. Base parameters are assembled from config.yaml:
         objective, max_depth, learning_rate, eval_metric
    2. self.device_info (set during __init__) is checked:
       - If GPU available: device="cuda", tree_method="hist"
       - If CPU only: device="cpu", tree_method="hist"
    3. The device selection is logged for transparency.


  10.4.4  Phase 4: Model Training & Early Stopping

    1. Training data is wrapped in an xgb.DMatrix (XGBoost's optimized
       data structure).
    2. xgb.train() is called with:
         - params: The parameter dictionary
         - dtrain: The DMatrix training data
         - num_boost_round: 100 (from n_estimators)
         - evals: Training set performance tracking
         - early_stopping_rounds: 10 (stop if no improvement for 10 rounds)
         - verbose_eval: True (log each round)
    3. Training completes when either:
         - All 100 rounds are finished, OR
         - Early stopping triggers (10 rounds without logloss improvement).


  10.4.5  Phase 5: Model Persistence (JSON)

    1. The trained model is saved using xgb.Booster.save_model():
         models/xgboost_model.json
    2. The JSON format stores:
         - All 100 decision tree structures
         - Split conditions (feature, threshold)
         - Leaf values (prediction contributions)
         - Model metadata (feature names, hyperparameters)
    3. JSON format is human-readable and portable across platforms.


10.5  Detection Process — Step by Step

  10.5.1  Input File Reception & Validation

    1. The input file is received via detect_mode(input_file) in run.py.
    2. InputHandler validates the file (existence, format).
    3. The file is processed into a DataFrame with 33 features.


  10.5.2  Feature Preparation & Alignment

    1. The feature list from config.yaml is retrieved.
    2. Any missing features in the DataFrame are filled with 0.0.
    3. Features are selected in the exact order expected by the model:
         X = df[feature_list].values
    4. The result is a numpy array with shape (n_flows, 33).


  10.5.3  Model Loading (Deserialization)

    1. XGBoostDetector is instantiated with config.
    2. The load() method is called with path: models/xgboost_model.json
    3. An empty xgb.Booster() is created.
    4. load_model() deserializes the JSON into the Booster object.
    5. If the file is not found, an error is logged and detection aborts.


  10.5.4  Prediction Execution (DMatrix)

    1. Input features are wrapped in xgb.DMatrix(X).
    2. model.predict(dtest) executes the trained ensemble:
         - Each flow passes through all 100 trees.
         - Each tree outputs a prediction contribution.
         - Contributions are summed and passed through sigmoid.
    3. Output: probability array with values between 0.0 and 1.0.


  10.5.5  Confidence Scoring

    1. Probabilities are thresholded at 0.5:
         preds = (probs > 0.5).astype(int)
    2. The probability value itself serves as the confidence score:
         - P = 0.99: Very confident DoS/DDoS detection
         - P = 0.51: Borderline detection (low confidence)
         - P = 0.02: Very confident Benign classification
    3. Both predictions (preds) and probabilities (probs) are returned
       to the Hybrid Engine for decision fusion.


10.6  Attack Detection Mechanism

  10.6.1  Benign vs Attack Traffic Characteristics

  XGBoost learns to distinguish benign from attack traffic by identifying
  feature patterns:

    +----------------------------+----------------+-------------------+
    | Feature                    | Benign         | DoS/DDoS          |
    +----------------------------+----------------+-------------------+
    | flow duration              | Variable       | Very short        |
    |                            | (seconds–min)  | (milliseconds)    |
    +----------------------------+----------------+-------------------+
    | total fwd packets          | Low–moderate   | Extremely high    |
    +----------------------------+----------------+-------------------+
    | fwd packet length std      | High variance  | Low variance      |
    |                            | (diverse sizes)| (uniform attack)  |
    +----------------------------+----------------+-------------------+
    | flow bytes/s               | Normal range   | Orders of         |
    |                            |                | magnitude higher  |
    +----------------------------+----------------+-------------------+
    | flow iat mean              | Variable       | Nearly zero       |
    |                            | (user-driven)  | (automated flood) |
    +----------------------------+----------------+-------------------+


  10.6.2  Decision Tree Example

  A simplified visualization of how one tree in the ensemble makes a
  decision:

    [flow bytes/s > 100000?]
          |             |
         YES            NO
          |             |
    [fwd pkt len     [flow iat mean
     std < 10?]       < 100?]
      |       |        |       |
     YES     NO       YES     NO
      |       |        |       |
    DoS   Benign     DoS   Benign
   (0.8)  (0.3)     (0.6)  (0.1)

  The actual trained model contains 100 such trees, each contributing a
  small prediction that is summed to produce the final probability.


  10.6.3  Feature Importance Rankings

  XGBoost internally tracks feature importance — which features contribute
  most to the split decisions. Based on the training on CIC-DDoS2019 data,
  the top features typically include:
    1. flow bytes/s (most discriminative)
    2. flow packets/s
    3. flow iat mean
    4. total fwd packets
    5. fwd packet length std


10.7  Supported Attack Types (10 Categories)

The XGBoost model is trained on 10 distinct DoS/DDoS attack types from
the CIC-DDoS2019 dataset:

  10.7.1  DNS Amplification
    - Protocol: UDP port 53
    - Mechanism: Small DNS queries with spoofed source IPs trigger large
      DNS responses directed at the victim.
    - Amplification factor: 28–54x
    - Key features: High flow bytes/s, large bwd packet lengths.

  10.7.2  LDAP Amplification
    - Protocol: UDP port 389
    - Mechanism: Exploits LDAP servers to reflect and amplify traffic.
    - Amplification factor: 46–55x
    - Key features: Extreme bwd packet length max, low fwd packet count.

  10.7.3  MSSQL Amplification
    - Protocol: UDP port 1434
    - Mechanism: MSSQL Browser Service used for reflection attacks.
    - Amplification factor: ~25x
    - Key features: Characteristic port usage, uniform packet sizes.

  10.7.4  NetBIOS Amplification
    - Protocol: UDP ports 137/138
    - Mechanism: NetBIOS name service queries used for amplification.
    - Amplification factor: 2.5–4x
    - Key features: Small total fwd packets, specific port patterns.

  10.7.5  NTP Amplification
    - Protocol: UDP port 123
    - Mechanism: Monlist command requests produce large response lists.
    - Amplification factor: 556x (one of the largest)
    - Key features: Extremely high bwd/fwd byte ratio.

  10.7.6  SNMP Amplification
    - Protocol: UDP port 161
    - Mechanism: GetBulkRequest commands generate large SNMP responses.
    - Amplification factor: 6–25x
    - Key features: High backward packet lengths, low forward counts.

  10.7.7  SSDP Amplification
    - Protocol: UDP port 1900
    - Mechanism: Simple Service Discovery Protocol search requests are
      reflected from UPnP devices.
    - Amplification factor: ~30x
    - Key features: Port 1900, multicast addresses.

  10.7.8  SYN Flood
    - Protocol: TCP
    - Mechanism: Half-open TCP connections overwhelm the victim's
      connection state table.
    - No amplification — direct volumetric attack.
    - Key features: Extremely high fwd psh flags = 0 (no data push),
      very short flow duration, high packets/s.

  10.7.9  TFTP Amplification
    - Protocol: UDP port 69
    - Mechanism: TFTP read requests trigger multi-packet file transfers
      to the spoofed source.
    - Amplification factor: ~60x
    - Key features: Large total length of bwd packets, multi-packet
      backward flows.

  10.7.10  UDP Flood
    - Protocol: UDP (various ports)
    - Mechanism: Volumetric flooding with random or targeted UDP packets.
    - No amplification — direct volumetric attack.
    - Key features: Extremely high flow packets/s, near-zero IAT,
      uniform packet sizes.


10.8  Per-Attack-Type Detection Rates

  +----------------------------+-------------------+
  | DNS Amplification          |   ~99%            |
  | LDAP Amplification         |   ~99%            |

  - Overall accuracy: >= 95% on known attack types.

10.10  Advantages & Limitations

  Advantages:
    - Extremely high accuracy on the 10 trained attack types.
    - Fast inference suitable for batch processing of large files.
    - Interpretable — feature importance and tree structures can be
      examined.
    - GPU acceleration for large-scale training.
    - Robust to noisy features and missing values.

  Limitations:
    - Cannot detect unknown (zero-day) attack types — only classifies
      patterns seen during training.
    - Binary classification only — does not identify the specific attack
      subtype (DNS vs LDAP vs NTP etc.), only "DoS" or "Not DoS".
    - Requires labeled training data — supervised learning depends on
      quality labeled datasets.
    - May overfit if max_depth or n_estimators are set too high.

  These limitations are addressed by the Kitsune autoencoder (Chapter 11)
  and the Hybrid Engine (Chapter 12).

CHAPTER 11 :  Kitsune AutoEncoder Model
────────────────────────────────────────────────────────────────────────────────

11.1  Model Overview & Justification

Kitsune is an unsupervised anomaly detection model based on a PyTorch
autoencoder neural network. Unlike XGBoost (which requires labeled data),
Kitsune learns only from benign traffic and flags anything that deviates
significantly from normal patterns as anomalous.

Why Kitsune was chosen:
  - Zero-day detection — can identify novel attacks never seen during
    training by measuring how "abnormal" traffic patterns are.
  - No attack labels needed — trains exclusively on benign data, making
    it independent of attack type catalogs.
  - Complementary to XGBoost — covers the critical gap where supervised
    models fail (unknown attack patterns).
  - Reconstruction-based scoring — provides a continuous anomaly score
    (RMSE) rather than a binary label, enabling nuanced decision making.
  - PyTorch implementation — supports GPU acceleration and modern deep
    learning best practices.

The Kitsune model is implemented across two classes in models/kitsune.py:
  - AutoEncoder (nn.Module): The neural network architecture.
  - KitNET: The training/detection wrapper class.


11.2  Conceptual Foundation (Anomaly Detection)

Kitsune operates on a fundamental principle:

  "If a model learns what NORMAL looks like, anything it cannot reproduce
   accurately is ABNORMAL."

The approach:
  1. Train the autoencoder to reconstruct benign traffic features.
  2. During detection, pass each flow through the encoder and decoder.
  3. Compare the original input to the reconstruction.
  4. If the reconstruction error (RMSE) is high, the input is "abnormal"
     — the model has never seen anything like it during training.

This is fundamentally different from XGBoost's approach:
  - XGBoost asks: "Does this look like a known attack?"
  - Kitsune asks: "Does this look like normal traffic?"


11.3  Autoencoder Neural Network Architecture

  11.3.1  Layer-by-Layer Breakdown

  The autoencoder consists of 4 linear layers organized in an
  encoder-decoder structure:

    Input (33 features)
         |
    +-----------+
    | Encoder   |
    |  Layer 1  |  Linear(33 → 24) + ReLU
    |  Layer 2  |  Linear(24 → 12) + ReLU
    +-----------+
         |
    [Bottleneck: 12 dimensions]
         |
    +-----------+
    | Decoder   |
    |  Layer 3  |  Linear(12 → 24) + ReLU
    |  Layer 4  |  Linear(24 → 33)
    +-----------+
         |
    Output (33 reconstructed features)


  The hidden dimensions are calculated from the hidden_ratio parameter:
    h_dim = int(input_dim × hidden_ratio) = int(33 × 0.75) = 24
    bottleneck = h_dim // 2 = 24 // 2 = 12


  11.3.2  Encoder (Compression)

  The encoder compresses the 33-feature input into a 12-dimensional
  latent representation:

    Layer 1: Linear(33 → 24) followed by ReLU activation
      - Reduces dimensionality while preserving important patterns.
      - ReLU introduces non-linearity, enabling the network to learn
        complex feature interactions.

    Layer 2: Linear(24 → 12) followed by ReLU activation
      - Further compresses to the bottleneck dimension.
      - Forces the network to learn only the most essential patterns
        of benign traffic.


  11.3.3  Bottleneck (Latent Space)

  The bottleneck is the 12-dimensional compressed representation:
    - Contains the "essence" of what makes traffic look normal.
    - During training, the network learns to encode benign patterns into
      this compact space.
    - Attack traffic produces distorted latent representations because
      the encoder has never learned to compress attack patterns.


  11.3.4  Decoder (Reconstruction)

  The decoder attempts to reconstruct the original 33 features from the
  12-dimensional bottleneck:

    Layer 3: Linear(12 → 24) followed by ReLU activation
      - Begins expanding back toward the original dimensionality.

    Layer 4: Linear(24 → 33) — no activation function
      - Produces the final reconstruction.
      - No activation on the final layer allows the output to match
        the full range of feature values.


11.4  Mathematical Algorithm

  11.4.1  RMSE (Root Mean Square Error)

  The anomaly score for each flow is the RMSE between the original input
  and its reconstruction:

    RMSE = sqrt( (1/n) × sum_i (x_i - x_hat_i)^2 )

  Where:
    - x_i = original feature value (input)
    - x_hat_i = reconstructed feature value (output)
    - n = number of features (33)

  Implemented in PyTorch as:
    scores = torch.sqrt(torch.mean((X_tensor - recons) ** 2, dim=1))


  11.4.2  Mean Squared Error (MSE) Loss

  During training, the loss function is MSE:

    MSE = (1/n) × sum_i (x_i - x_hat_i)^2

  The optimizer (Adam) minimizes MSE over all training batches, teaching
  the network to reconstruct benign traffic as accurately as possible.


  11.4.3  Dynamic Threshold Calculation (mu + k*sigma)

  After training, the anomaly threshold is calculated from the training
  data's reconstruction errors:

    threshold = mu_RMSE + k × sigma_RMSE

  Where:
    - mu_RMSE = mean RMSE across all benign training samples
    - sigma_RMSE = standard deviation of RMSE across training samples
    - k = threshold_std_factor (config.yaml) = 3.0

  With k = 3.0, the threshold corresponds to 99.7% of the normal
  distribution (3-sigma rule). This means:
    - 99.7% of benign flows will have RMSE below the threshold.
    - Only 0.3% of benign flows may be false positives.
    - Attack traffic, which produces high RMSE, will exceed the threshold.


11.5  Hyperparameters Configuration

  11.5.1  learning_rate, hidden_ratio

  +----------------------+--------+------------------------------------------+
  | Parameter            | Value  | Purpose                                  |
  +----------------------+--------+------------------------------------------+
  | learning_rate        | 0.001  | Adam optimizer step size. Controls how    |
  |                      |        | fast the network adjusts weights.        |
  +----------------------+--------+------------------------------------------+
  | hidden_ratio         | 0.75   | Ratio of hidden layer size to input      |
  |                      |        | dimension. h_dim = 33 × 0.75 = 24.      |
  +----------------------+--------+------------------------------------------+


  11.5.2  threshold_std_factor

  +----------------------+--------+------------------------------------------+
  | Parameter            | Value  | Purpose                                  |
  +----------------------+--------+------------------------------------------+
  | threshold_std_factor |  3.0   | Number of standard deviations above the  |
  |                      |        | mean for the anomaly threshold.          |
  |                      |        | Higher = less sensitive (fewer alerts).   |
  |                      |        | Lower = more sensitive (more alerts).    |
  +----------------------+--------+------------------------------------------+

  Tuning guidelines:
    - k = 2.0: Sensitive. Catches subtle anomalies but may produce false
      positives on unusual-but-benign traffic.
    - k = 3.0: Balanced (default). Good trade-off between detection and
      false positive rates.
    - k = 4.0: Conservative. Only flags extreme anomalies. Lower false
      positive rate but may miss subtle attacks.


11.6  Training Process — Detailed Walkthrough

  11.6.1  Phase 1: Benign Data Preparation

  Training begins in the train_kitsune() function (run.py):
    1. Load benign traffic: Dataset/PolishedBenign/Polished_benign.csv
    2. Drop the label column (unsupervised — no labels needed).
    3. Convert to numpy array X_benign.
    4. If dataset exceeds 50,000 samples, subsample to 50k to prevent
       excessive training time.


  11.6.2  Phase 2: Model Initialization & Device Selection

    1. Input dimension is determined: input_dim = number of features (33).
    2. KitNET is instantiated with input_dim and kitsune config.
    3. AutoEncoder(33, hidden_dim=0.75) creates the 4-layer network.
    4. Device is selected:
         - torch.cuda.is_available() → cuda (GPU)
         - Otherwise → cpu
    5. Model is moved to the selected device: model.to(device)
    6. Adam optimizer is initialized with learning_rate = 0.001.
    7. MSELoss criterion is set.


  11.6.3  Phase 3: Training Loop (Epochs & Batches)

    1. Training data is converted to a PyTorch FloatTensor.
    2. A DataLoader is created with batch_size=32 and shuffle=True.
    3. For each epoch (default: 10 epochs):
       a. For each batch:
          - Zero the optimizer gradients.
          - Forward pass: outputs = model(inputs)
          - Compute loss: MSE between inputs and outputs.
          - Backward pass: loss.backward()
          - Update weights: optimizer.step()
          - Accumulate batch loss.
       b. Every 5 epochs, log the average loss.
    4. The model learns to reconstruct benign traffic features.


  11.6.4  Phase 4: Threshold Calculation

  After training completes:
    1. Set model to eval mode (disables dropout, batchnorm if present).
    2. Run all training data through the model (no gradients).
    3. Compute RMSE per sample:
         loss = sqrt(mean((X - reconstruction)^2, dim=1))
    4. Convert to numpy array.
    5. Calculate threshold:
         mean_loss = np.mean(loss_np)
         std_loss = np.std(loss_np)
         threshold = mean_loss + 3.0 × std_loss
    6. Log the threshold, mean, and std values.


  11.6.5  Phase 5: Model Persistence (PKL)

    1. The model state is packaged into a dictionary:
         - model_state: PyTorch state_dict (weights and biases)
         - threshold: Computed anomaly threshold
         - input_dim: 33
         - config: Kitsune configuration dictionary
    2. Serialized using Python's pickle module:
         models/kitsune_model.pkl
    3. SHA-256 checksum is computed and saved:
         models/kitsune_model.pkl.sha256
    4. The checksum ensures model integrity — if the .pkl file is
       corrupted or tampered with, loading will fail with a clear error.


11.7  Detection Process — Step by Step

  11.7.1  Model Loading & Restoration

    1. KitNET.load(path) is called as a classmethod.
    2. File existence is verified.
    3. Checksum verification:
       a. Read expected hash from .sha256 file.
       b. Compute SHA-256 of the .pkl file.
       c. Compare: if mismatch, raise ValueError (corruption/tampering).
       d. If no checksum file exists, log warning and proceed.
    4. Deserialize the pkl file:
       a. Reconstruct KitNET instance with saved input_dim and config.
       b. Load model weights via model.load_state_dict().
       c. Restore the saved threshold.
       d. Set model to eval mode.


  11.7.2  Input Processing & Tensor Conversion

    1. Input features (numpy array X) are received from the Hybrid Engine.
    2. Converted to PyTorch FloatTensor:
         X_tensor = torch.FloatTensor(X).to(device)
    3. Tensor is moved to the appropriate device (CPU or GPU).


  11.7.3  Reconstruction (Forward Pass)

    1. Model is set to eval mode.
    2. torch.no_grad() context — no gradient computation needed.
    3. Forward pass: recons = model(X_tensor)
       - X_tensor passes through encoder → bottleneck → decoder.
       - Output shape matches input: (n_flows, 33).


  11.7.4  Anomaly Scoring (RMSE)

    1. Compute per-flow RMSE:
         scores = sqrt(mean((X_tensor - recons)^2, dim=1))
    2. Convert to numpy array:
         return scores.cpu().numpy()
    3. Each flow now has a continuous anomaly score:
         - Low RMSE (e.g., 0.01): Normal traffic (well-reconstructed).
         - High RMSE (e.g., 5.0): Anomalous traffic (poorly reconstructed).


  11.7.5  Threshold Comparison & Verdict

  The Hybrid Engine (Chapter 12) performs the comparison:
    - If RMSE > threshold: Flag as "Anomaly"
    - If RMSE <= threshold: No anomaly flag

  The verdict is not made by Kitsune alone — the Hybrid Engine combines
  this with XGBoost's prediction to produce the final classification.


11.8  How Kitsune Detects Attacks

  11.8.1  Feature Distribution Mismatch

  Attack traffic has fundamentally different feature distributions than
  benign traffic:
    - Benign flows: Moderate packets, variable sizes, human-driven timing.
    - Attack flows: Extreme packets, uniform sizes, machine-driven timing.

  The autoencoder, trained only on benign patterns, cannot accurately
  reconstruct attack features, resulting in high RMSE.

  11.8.2  Pattern Novelty

  Because Kitsune has never seen attack traffic during training, any
  attack-like pattern is "novel" to the model. The encoder cannot
  compress it into the learned latent space, and the decoder cannot
  reconstruct it — producing high reconstruction error.

  11.8.3  Statistical Outliers

  Even subtle attacks that share some characteristics with benign traffic
  will have at least a few features that fall outside the training
  distribution. The RMSE aggregates errors across all 33 features, making
  it sensitive to multi-dimensional anomalies.

  11.8.4  Attack Type Detection Examples

    - DNS Amplification: Large bwd_packet_length and extreme flow bytes/s
      are never seen in benign training data → high RMSE.
    - SYN Flood: Near-zero flow iat mean with zero backward packets creates
      a pattern the autoencoder cannot reconstruct.
    - Zero-Day: Even previously unknown attack types will produce unusual
      feature combinations that increase reconstruction error.


11.9  Process Segmentation (Training & Detection Phases)

  Training Phase:
    Input: Benign traffic only
    Process: Learn to reconstruct benign patterns
    Output: Trained model + anomaly threshold
    Frequency: Once (or retrain when baseline changes)

  Detection Phase:
    Input: Unknown traffic (mixed benign/attack)
    Process: Reconstruct each flow, compute RMSE
    Output: Anomaly scores per flow
    Frequency: Every detection run


11.10  Performance Characteristics & Accuracy

  - Anomaly detection rate: Reliably detects traffic that deviates
    significantly from benign baseline.
  - False positive rate: ~0.3% (by design, 3-sigma threshold).
  - Inference speed: ~0.5ms per flow (CPU), ~0.05ms per flow (GPU).
  - Model size: ~50-100 KB (pkl format).
  - Training time: ~10-30 seconds on 50k benign samples.


11.11  Advantages & Limitations

  Advantages:
    - Detects zero-day attacks — no prior knowledge of attack patterns
      required.
    - Continuous anomaly scoring — provides granularity beyond binary
      classification.
    - Small model size and fast inference.
    - GPU-accelerated training and detection via PyTorch.
    - Model integrity verification through SHA-256 checksums.

  Limitations:
    - Cannot identify the specific attack type — only says "anomalous"
      or "normal."
    - Sensitive to the quality of benign training data — contaminated
      training data will raise the threshold and reduce sensitivity.
    - May flag legitimate unusual traffic as anomalous (false positives
      for rare-but-benign patterns).
    - Threshold requires tuning per deployment environment.

  These limitations are addressed by combining Kitsune with XGBoost
  through the Hybrid Engine (Chapter 12).


11.12  Threshold Tuning Guidelines

  The threshold_std_factor parameter controls sensitivity:

  +----------+--------------+------------------+---------------------+
  | k value  | Sensitivity  | FP Rate (approx) | Use Case            |
  +----------+--------------+------------------+---------------------+
  |  2.0     | High         | ~5%              | Critical systems    |
  |          |              |                  | where missing an    |
  |          |              |                  | attack is costly.   |
  +----------+--------------+------------------+---------------------+
  |  3.0     | Balanced     | ~0.3%            | Default. Good for   |
  |          | (default)    |                  | most deployments.   |
  +----------+--------------+------------------+---------------------+
  |  4.0     | Low          | ~0.01%           | High-traffic        |
  |          |              |                  | environments where  |
  |          |              |                  | false positives are |
  |          |              |                  | operationally       |
  |          |              |                  | expensive.          |
  +----------+--------------+------------------+---------------------+

  To tune: Run detection on a known-benign dataset. If false positive rate
  is too high, increase k. If detection rate on known attacks is too low,
  decrease k.

CHAPTER 12 :  Hybrid Decision Engine
────────────────────────────────────────────────────────────────────────────────

12.1  What is the Hybrid Engine?

The Hybrid Decision Engine (models/hybrid.py) is the central intelligence
component that combines outputs from both XGBoost and Kitsune to produce
a single, unified verdict for each network flow. It implements decision
fusion, heuristic overrides, and confidence scoring.

The HybridDetector class orchestrates the entire detection pipeline by:
  1. Running both models on the same input data.
  2. Applying hierarchical decision logic.
  3. Overriding false positives with heuristic safety checks.
  4. Generating human-readable reason strings for each decision.


12.2  Why the Hybrid Engine Was Needed

  12.2.1  The Single-Model Problem

  Using only XGBoost:
    - Misses zero-day attacks (unseen patterns).
    - Cannot detect novel attack types not in training data.

  Using only Kitsune:
    - Cannot identify the specific attack type.
    - May flag unusual-but-benign traffic as anomalous.
    - Lower precision compared to supervised classification.


  12.2.2  The Hybrid Solution

  By combining both models, the system achieves:
    - Known attack detection via XGBoost (high precision).
    - Unknown attack detection via Kitsune (high coverage).
    - Reduced false positives through heuristic overrides.
    - Comprehensive verdict with confidence scoring.


12.3  Hybrid Engine Architecture

  12.3.1  System Components Diagram

    +-----------------------------------------------------------+
    |                   HYBRID DECISION ENGINE                  |
    |                                                           |
    |  +------------------+    +------------------+             |
    |  |   XGBoost        |    |   Kitsune         |            |
    |  |   Classifier     |    |   Autoencoder     |            |
    |  |                  |    |                   |            |
    |  |  Input: X (33f)  |    |  Input: X (33f)   |            |
    |  |  Output:         |    |  Output:          |            |
    |  |   - preds (0/1)  |    |   - RMSE scores   |            |
    |  |   - probs (0-1)  |    |   - threshold     |            |
    |  +--------+---------+    +--------+----------+            |
    |           |                       |                       |
    |           +----------+------------+                       |
    |                      |                                    |
    |              +-------v--------+                           |
    |              | Decision Fusion|                           |
    |              | Logic          |                           |
    |              +-------+--------+                           |
    |                      |                                    |
    |              +-------v--------+                           |
    |              | Heuristic      |                           |
    |              | Override System|                           |
    |              +-------+--------+                           |
    |                      |                                    |
    |              +-------v--------+                           |
    |              | Verdict        |                           |
    |              | Generator      |                           |
    |              +----------------+                           |
    |                                                           |
    |  Output: final_preds[], reasons[], scores                 |
    +-----------------------------------------------------------+


  12.3.2  Model Orchestrator

  The detect() method runs both models sequentially:
    1. xgb_preds, xgb_probs = self.xgb.predict(X)
    2. kitsune_scores = self.kitsune.predict(X)

  Both models receive the same feature matrix X (33 features) and operate
  independently — neither model's output influences the other's execution.


  12.3.3  Decision Fusion Logic

  For each flow i, the decision logic follows this hierarchy:

    Priority 1 — XGBoost DoS Detection:
      If xgb_label == 1 (DoS/DDoS):
        verdict = "DoS/DDoS"
        reason = "XGBoost Confidence: {probability}"

    Priority 2 — Kitsune Anomaly Detection:
      If xgb_label == 0 AND kitsune_score > threshold:
        verdict = "Anomaly"
        reason = "Kitsune RMSE: {score} > {threshold}"

    Priority 3 — Clean Traffic:
      If xgb_label == 0 AND kitsune_score <= threshold:
        verdict = "Benign"
        reason = "Clean"


  12.3.4  Heuristic Override System

  After the initial verdict, the _is_safe_broadcast() method checks for
  false positives caused by normal network broadcasts:

    Override condition:
      - verdict != "Benign" (flow was flagged)
      - input_df is available (raw data with IP/port columns)
      - Flow matches safe broadcast profile

    Safe broadcast criteria:
      1. Volume check: total fwd packets <= 10 (low volume).
         If volume exceeds 10, the flow is NOT considered a safe
         broadcast and the override does not apply.
      2. IP check: Destination is broadcast (.255) or multicast
         (224.x.x.x, 239.x.x.x, or 255.255.255.255).

    The code also computes a safe port set ({137, 138, 1900, 5353,
    67, 68}) but the current return logic does not use the port check
    — the decision is based solely on volume + IP pattern.

    If criteria 1 AND criteria 2 are met:
      verdict = "Benign"
      reason = "Clean (Safe Broadcast)"


  12.3.5  Verdict Generator

  The final output dictionary contains:
    - xgb_preds: Array of XGBoost binary predictions (0/1).
    - xgb_probs: Array of XGBoost probability scores.
    - kitsune_scores: Array of Kitsune RMSE values.
    - final_preds: Array of final verdicts ["Benign", "DoS/DDoS", "Anomaly"].
    - reasons: Array of human-readable explanation strings.


12.4  Roles & Responsibilities

  +-------------------+----------------------------------------------+
  | Component         | Responsibility                               |
  +-------------------+----------------------------------------------+
  | XGBoost           | Classify known attack types with high        |
  |                   | precision. Provide confidence probability.   |
  +-------------------+----------------------------------------------+
  | Kitsune           | Detect unknown/novel attacks by measuring    |
  |                   | deviation from benign baseline.              |
  +-------------------+----------------------------------------------+
  | Decision Fusion   | Combine both outputs using priority-based    |
  |                   | hierarchical logic.                          |
  +-------------------+----------------------------------------------+
  | Heuristic Override| Prevent false positives from safe broadcast  |
  |                   | and multicast traffic.                       |
  +-------------------+----------------------------------------------+
  | Verdict Generator | Produce final classification and human-      |
  |                   | readable reason for each flow.               |
  +-------------------+----------------------------------------------+


12.5  Step-by-Step Operation

  12.5.1  Step 1: Input Reception

    - The detect() method receives:
      - X: numpy array of shape (n_flows, 33) — feature values.
      - input_df: Optional pandas DataFrame with raw data including
        IP addresses and ports (for heuristic checks).


  12.5.2  Step 2: Parallel Model Execution

    - XGBoost predict(X) → returns preds (binary) and probs (probability).
    - Kitsune predict(X) → returns RMSE scores per flow.
    - Both models process all flows at once (vectorized).


  12.5.3  Step 3: Decision Fusion

    For each flow i (loop over len(X)):
      1. Read xgb_label = xgb_preds[i]
      2. Read k_score = kitsune_scores[i]
      3. Read k_thresh = self.kitsune.threshold
      4. Apply priority-based logic:
           XGBoost says DoS → "DoS/DDoS"
           Kitsune says anomaly → "Anomaly"
           Otherwise → "Benign"


  12.5.4  Step 4: Heuristic Override Application

    For each flow where verdict != "Benign":
      1. Check if input_df is available.
      2. Call _is_safe_broadcast(input_df.iloc[i]).
      3. If safe broadcast: override to "Benign (Safe Broadcast)".


  12.5.5  Step 5: Result Compilation

    Assemble the results dictionary:
      - xgb_preds, xgb_probs, kitsune_scores
      - final_preds: The definitive verdict for each flow
      - reasons: Human-readable explanation for each verdict
    Return to the orchestrator (run.py) for reporting.


12.6  Features of the Hybrid Engine

  12.6.1  Hierarchical Decision Making (4 Priority Levels)

    Level 1: XGBoost Detection (highest priority for known attacks)
    Level 2: Kitsune Anomaly Detection (for unknown patterns)
    Level 3: Heuristic Override (to correct known false positive cases)
    Level 4: Default Benign (lowest priority — clean traffic)


  12.6.2  Safe Broadcast Detection

  The _is_safe_broadcast() method prevents common false positives by
  overriding the verdict when traffic is low-volume (<=10 packets) and
  destined to a broadcast (.255) or multicast (224.x / 239.x /
  255.255.255.255) IP address.

  Typical false positive scenarios include:
    - NetBIOS name resolution on broadcast addresses.
    - SSDP discovery on multicast addresses.
    - mDNS queries on multicast addresses.
    - DHCP requests on broadcast addresses.

  These are normal network operations that may trigger anomaly detection
  due to their broadcast/multicast nature, but are not malicious.


  12.6.3  Confidence Scoring

  Each verdict comes with associated confidence information:
    - DoS/DDoS: XGBoost probability (e.g., "Confidence: 0.98")
    - Anomaly: Kitsune RMSE vs threshold (e.g., "RMSE: 2.15 > 0.89")
    - Benign: Simply "Clean" or "Clean (Safe Broadcast)"


  12.6.4  Detailed Reasoning Generation

  Every flow receives a human-readable reason string:
    - "XGBoost Confidence: 0.97"
    - "Kitsune RMSE: 3.42 > 0.89"
    - "Clean"
    - "Clean (Safe Broadcast)"

  These reasons are written to the prediction JSON files and the summary
  report, enabling security analysts to understand why each flow was
  classified.


12.7  Inter-Model Communication

  12.7.1  Input Interface

  Both models receive the same input:
    - Data type: numpy array
    - Shape: (n_flows, 33)
    - Content: The 33 selected features from config.yaml

  The Hybrid Engine does not transform the data between models — both
  operate on the identical feature matrix.


  12.7.2  Output Interface

  The Hybrid Engine returns a dictionary to run.py:

    {
      "xgb_preds":      [0, 1, 0, ...],     # Binary predictions
      "xgb_probs":      [0.02, 0.98, ...],   # Probabilities
      "kitsune_scores": [0.01, 0.05, ...],   # RMSE values
      "final_preds":    ["Benign", "DoS/DDoS", ...],  # Verdicts
      "reasons":        ["Clean", "XGBoost Confidence: 0.98", ...]
    }


  12.7.3  XGBoost ↔ Hybrid ↔ Kitsune Data Flow

    run.py
      |
      +--> HybridDetector.detect(X, input_df)
             |
             +--> XGBoostDetector.predict(X)
             |      Returns: preds, probs
             |

  12.8.1  Known DDoS Attack

  Accuracy improvement from hybrid approach:

12.10  Configuration & Tuning (Operational Modes)

  The Hybrid Engine behavior can be tuned through config.yaml:

    - thresholds.malicious_file_ratio (0.30):
      Percentage of malicious/anomalous flows needed to flag a file as
      Malicious. Used in the report generation stage.

    - kitsune.threshold_std_factor (3.0):
      Controls Kitsune's anomaly sensitivity. Directly affects how many
      flows are flagged as "Anomaly" by the hybrid logic.

    - Adding safe ports to _is_safe_broadcast():
      Additional service ports can be added to the safe_ports set to
      reduce false positives for known network services.


12.11  Advantages of the Hybrid Approach

  1. Defense in Depth — Two independent detection methods provide
     redundancy. If one model fails, the other provides coverage.

  2. Known + Unknown Coverage — XGBoost handles the 10 known attack types
     with high precision. Kitsune catches everything else.

  3. Explainable Decisions — Every verdict includes a reason string
     that explains which model triggered the detection and why.

  4. Low Overhead — The hybrid logic adds negligible processing time
     compared to the model inference itself.

  5. Configurable Sensitivity — Both the classification threshold (0.5)
     and anomaly threshold (mu + k*sigma) can be tuned independently.

  6. False Positive Mitigation — Heuristic overrides prevent common
     network services from being misclassified.
